作成日: 2026-05-17

■ コンセプト（更新版）
----------------------------------------------------------------
当初案：「標準ルーブリックを我々が提供し、エージェントに使わせる」

更新後：「既成評価基準を束ねる配管を提供する」
- 我々は基準を作らない（独自軸を立てない）
- 既存基準（OWASP / CVSS / OpenSSF Scorecard / Lighthouse /
  DORA / FAIR 等）をモジュールとして取り込む
- エージェントが選択・ブレンド・トグル切替で運用
- DCP pipeline / $V ゲーティング / Shadow Layer の応用ケース

提供するのは "評価標準" ではなく "評価基準を扱う配管"。
基準の真贋判定は基準コミュニティが負い、
我々は配管の品質を負う。責任分界が綺麗になる。

■ 当初案の問題点（議論で明確化）
----------------------------------------------------------------
[問題1] 独自ルーブリックは主観の塊になる
  - 「セキュリティ」「UX」はカテゴリ名であって観測量ではない
  - 観測手順への翻訳に主観が混入する
  - 我々が一貫して避けてきた「主観的重み付け」が裏口から入る

[問題2] Goodhart 問題が構造的に避けられない
  - 標準化は必ず最適化対象になる
  - 「観測されることで対象が変質する」設計は、
    我々の他のシステム（観測が対象に影響しない）と哲学的に逆向き

[問題3] 大衆需要とのミスマッチ
  - 市場の多数派が求めるのは「自分が考えなくて済むもの」
  - 我々の硬派路線は使う側に判断意欲を要求する
  - これは譲ると本体が壊れる種類の制約

→ 当初案の「標準ルーブリック提供」路線は採用しない。

■ 採用路線：基準配管型（Rubric Pipeline）
----------------------------------------------------------------
構造：

[評価対象]
    ↓
[Normalizer 層]　//どの程度　基準をローディングするか初期設定、基準の初期化、ローディングが重いと仮定している
  - 各既成基準の機械測定を実行
  - 入力形式を統一スキーマに正規化
  - DCP の Normalizer 思想と同型
    ↓
[Shadow 層]
  - 基準ごとの中間スコアを並列保持
  - VCP Shadow Layer の staging + derivation を流用 //どちらかというと DCP $Vゲートテクニック？
  - トグル On/Off で基準を有効化／無効化
  - 一度計算した素スコアは保持されるため切替は軽量
    ↓
[$V ゲーティング層]
  - 用途別レンズ（個人 / 業務 / 教育 / 監査）が
    基準セットのウェイトを変調
  - Persona と同じ perceptual lens 切替
  - 単一の正解ウェイトは提供しない（プリセットのみ）
    ↓
[ブレンディング層]
  - percentile/quantile 正規化で合成
  - 絶対値の意味を捨て、相対順位を保つ
  - 「対象群内の上位 X%」として比較可能性を担保
    ↓
[出力層]
  - スコア + 根拠（観測量）+ 使用基準リスト + ウェイト
  - レポートに rubrics-used / weights を必ず同梱
  - DCP $S 宣言と同じ「成果物が評価基準を背負う」設計


■ 既成基準の見立て（着手判断の前提）
----------------------------------------------------------------
分野別の既存資産の厚み：

セキュリティ系（厚い）
  - OWASP Top 10 / OWASP ASVS
  - CVSS
  - CIS Benchmarks
  - SLSA

サプライチェーン／メンテ健全性（厚い、機械化済）
  - OpenSSF Scorecard
  - npm audit / pip-audit
  - Libraries.io SourceRank

コード品質系（中程度）
  - Lighthouse
  - ESLint / RuboCop / Clippy
  - SonarQube Quality Gates
  - ISO/IEC 25010（包括的だが抽象的）

ドキュメント／UX 系（薄い）
  - Awesome README 系慣習
  - The Good Docs Project
  - Nielsen 10 原則
  - WCAG

研究／学術系（中程度）
  - ML Reproducibility Checklist
  - FAIR data principles

プロセス／組織系（中程度）
  - DORA Four Keys
  - SPACE フレームワーク

→ 分布が偏っているため「全領域カバー」は破綻する。
   「厚い分野を束ねる配管」としてなら成立する。

■ 隠れた重大課題：スコア空間の正規化
----------------------------------------------------------------
- CVSS は 0–10
- OpenSSF Scorecard は 0–10
- Lighthouse は 0–100
- OWASP Top 10 は順位（カテゴリ）
- ISO 25010 は定性記述

これらを同じ空間に揃える変換規則に主観が入り込む危険。
MSW で議論した「表現空間が違うものを統一しようとすると壊れる」
問題と同型。

解の方向：
  (a) 正規化を諦め、基準ごとの素スコアを並列表示
      → 統合単一スコアは作らない
  (b) percentile/quantile に変換してから合成
      → 絶対値の意味は失うが、相対順位は保てる

採用予定：(b)
  理由：「比較可能性」が本企画の本旨であり、
        絶対値より相対順位のほうが目的に合う。

■ 既存資産との接続（更新）
----------------------------------------------------------------
- DCP / dcp-wrap：Normalizer 層 / 出力層スキーマでそのまま
- Shadow Layer (VCP)：基準ごとの中間スコア並列保持で
  トグル切替を軽量化
- Persona (Engram)：用途別レンズの perceptual lens 切替
- Engram 代謝：レビュー履歴ノードの自然風化
- $V ゲーティング：ウェイトの動的変調

→ 既存資産の応用ケースとして筋が良い。
   独自要素は配管設計のみで、評価基準そのものは作らない。

■ やってはいけない方向（議論で明確化）
----------------------------------------------------------------
[NG1] 独自軸を追加する
  → 我々の主観が混入する。基準は既成のものに限る。

[NG2] 統合単一スコアを主張する
  → Goodhart の餌になる。比較可能性は順位で担保する。

[NG3] 「正解の重みベクトル」を提供する
  → 用途別レンズはあくまでデフォルトプリセット。
    「正解」を主張しない。

[NG4] 緩和して大衆向けにする
  → 緩和すると本体が壊れる。難解さは設計の必然的帰結。
    使う側に判断意欲を要求する道具のままでよい。

■ 着手判断（更新）
----------------------------------------------------------------
ステータス：保留（仕込み型）

理由：
  - 大衆需要とミスマッチ（ランキングサイト等の安直解で代替される）
  - Engram / MSW / VCP の現行作業を中断してまでやる優先度ではない
  - ただし配布物が陳腐化しにくい型の仕事として筋は良い

機が熟す条件：
  - 安直なランキング／スコアリングサービスの限界が顕在化したとき
  - 監査／コンプライアンス／調達評価領域で
    「再現可能・追跡可能な評価」のニーズが顕在化したとき
  - Engram Persona / VCP Shadow Layer の実装が安定し、
    応用ケースとして無理なく着手できるとき

事前準備（気が向いたとき数時間で実施可能）：
  - 既成基準 20-30 個のサーベイリスト作成
  - 機械観測可能性のマーキング
  - percentile 正規化方針の具体化

→ サーベイが書き切れるか否か = 着手判断のリトマス試験紙。

追補（2026-05-17 続き議論）— $ST / Shadow Reference / 配布形態
================================================================

■ $ST 蓄積層の導入案
----------------------------------------------------------------
DCP の $ST（状態蓄積）概念を取り込み、評価を「一度きりの測定」
ではなく「周回による像の収束」として扱う。

  [Probe Dispatcher] → 外部API群へ並列発射
  [Normalizer]       → 各レスポンスを DCP $S 化
  [DCP Pipeline]     → ゲート群を周回
  [$ST 蓄積]         → 周回ごとの差分・トレンド・分散収束
  [収束判定で停止 or 次の API へ]

Shadow Layer は「基準ごとの素スコア並列保持（空間方向）」、
$ST は「周回経過の状態蓄積（時間方向）」で直交。両立可能。

ただし $ST が活きるのは「周回することで像が更新される」基準のみ。
CVSS 単発スキャンのような「一発測定で終わる基準」には過剰設計。
→ 周回が意味を持つ基準と単発で終わる基準を分けて配管する。

■ 外部 API 依存の回避 — Shadow Reference Set 構想
----------------------------------------------------------------
外部 API への永続依存はブラックボックス化と rate limit の二重リスク。
解：我々が一度だけ叩き、Shadow コピーとしてバージョニング保存。
以降はローカルで DCP pipeline に通す。

シミュレート可能性の三分類：

[A] 完全シミュレート可能（決定論的・公開アルゴリズム）
    - OpenSSF Scorecard / npm audit / pip-audit
    - ESLint / RuboCop / CVSS 計算
    → 実装は薄いラッパで済む。Shadow 化が綺麗に成立。

[B] 部分シミュレート可能（観測時点の状態が必要）
    - Lighthouse（環境依存）
    - GitHub stars/velocity（時点依存）
    → 「いつ時点の Shadow か」をメタデータに同梱。
       新規評価時に 1 回だけ外部実行、比較は Reference Set で。

[C] シミュレート困難（外部判断依存）
    - Snyk / SonarQube cloud / WCAG 手動項目
    → サーベイ段階で除外。

n × n リファレンスアプリ案の解釈：
  解釈1（採用）: API レスポンスをそのまま Shadow 化（記録型）
    → percentile 正規化の基準群として機能
  解釈2（不採用）: API 挙動を学習して再現（モデル化型）
    → LLM 推論代替と同じ罠。透明性を失う。

■ 実装重さの見立て
----------------------------------------------------------------
- [A] 系は薄いラッパで軽い（数十～数百行規模）
- [B] 系は「新規評価時に 1 回だけ外部実行 + Reference で比較」で軽量化
- [C] 系は実装コスト 0（除外）

重さの本丸は個別 Shadow 化ではなく、Reference Set 構築維持：
  - 多様性ある n 個の選定
  - バージョニング規約
  - Shadow Set のサイズ管理

アピール性の弱点：
  Shadow 化単体ではユーザから「ローカル実行ツール」と区別がつかない。
  付加価値が見えるのは percentile ブレンドと $ST 周回の方。
  → Shadow 化は透明性保険として後景、表に出すのは束ね方と周回。

■ 配布形態の比較
----------------------------------------------------------------
[MCP 形態]
  + 既存資産と同じ配布チャネル、ローカル完結、開発コスト最小
  - 可視性ゼロ、拡散しない、$ST 周回の旨味が出にくい

[サイト形態]
  + percentile 分布・周回経過・レンズ切替を画面で可視化
  + 「触れる」「シェアされる」心理的価値
  + 本企画の哲学を可視化できる唯一の形
  - 運用コスト発生、ランキングサイトのレッドオーシャン懸念

[API 形態]
  + 機械間連携素材として汎用
  - 単独では成立せず、外部 API 依存を嫌った哲学と捻れる

アピール順序：サイト > MCP > API
理想は三層構造（サイトをフロント / MCP を窓口 / API は副産物）。
ただし仕込みフェーズで全部作る話ではない。

着手順序の筋：
  1. サーベイで [A][B][C] 振り分けを確定
  2. 1 領域で Reference Set prototype（例：セキュリティ）
  3. サイト形態で 1 領域だけ可視化
  4. その後 MCP / API を派生

「需要顕在化したら作る」→「需要顕在化したらサイトを立てる」
に読み替えるのが正確。仕込み型から少しはみ出す覚悟が必要。

■ 企画の本質再評価 — DCP 応用 vs 問題解決
----------------------------------------------------------------
この企画は **DCP 応用ケースの探索** であって、
**評価という問題への解答ではない**。

根拠：
  - 議論重心が「評価のどこに困っているか」ではなく
    「DCP 部品をどう繋ぐか」に移っていった
  - 採用構造（Normalizer→Shadow→$V→Blending→Output→$ST）は
    DCP 既存部品の組み合わせそのもの
  - 評価対象領域は既成基準が代行、我々が新規に解く問題は無い
  - 「誰が何の判断で誤誘導されているか」が一度も問われなかった

価値の分離：
  - DCP 応用としての価値 → 高い（配管の一貫性、資産再利用、透明性）
  - 評価領域の市場ニーズ → 不明（断片化、既存ソリューションで部分充足）

世間ニーズが見えないのは正常な観察。実際にこの領域に
クリアな単一ニーズは無い。あるのは断片化された需要群
（コンプライアンス、調達、OSS 採用、教育）で、それぞれが
既存ソリューションで部分的に満たされている。

「全部束ねる配管」は技術的には綺麗だが、
束ねたものを欲しがる単一顧客像が無い。
Engram / MSW と共通する構造的弱点：
「美しい配管を作るが、客が分散している」パターン。
