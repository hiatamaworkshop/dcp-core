dcp-wrap の最終コミットは 2026-05-28 で、以後の実装の知見は dcp-lighthouse に溜まっている。
本文書は、wrap を概念と仕様の持ち主として位置づけ直し、lighthouse で確かめられたことを wrap の構想へ戻すための整理である。

## 2. draft「ブレインとシャドウの作法」は lighthouse でどこまで確かめられたか

出典の列の「draft」は本リポジトリ `PIPELINE_ARCHITECTURE.md` の同名の節、「pipeline.md」は dcp-docs の
Shadow weight pattern と Predictive Control Pattern の節である。後者は draft ではないが、同じ構想の片割れとして並べる。

| 主張 | 出典 | lighthouse での状況 |
|---|---|---|
| 推論の線を「観測、予測」と「解釈、決定」の間に引く | draft | 到達目標として採った（2026-10-08）。灯台は観測と予見を数理だけで、較正つきで行う層とした |
| シャドウは推論ゼロの短期予測バッファ、`$F`（新チャネル候補）で出す | draft | 未実装（コード検索で確認）。F2 として予定。curator の予測分布を horizon と信頼度つきで出す |
| `$O` 分岐の仮想ストリーム、予測制御 | pipeline.md | 較正ハーネスの変換（注入、シャッフル、トレース単位の間引き）が同じ形をしている。F3 で本番と並走する常設の流れにする予定 |
| 予測制御の判断は閾値との比較（例 `pessimistic < 0.80`） | pipeline.md | 比較の外れ方を測った。package 単位で誤警報 29%（07-28）、RC レンズで 41%（09-27）、実データで事象の独立を仮定すると 99.8%（10-06）。較正をしないと「統計に裏付けられた判断」は成り立たない |
| 検証のタイミングは $R ファンアウトの実装時 | draft | wrap では検証されず、lighthouse の実データ較正期間（2026-09-27 事前登録）で確かめている |
| Brain は数値を読んで判断し、推測しない | pipeline.md | 過分散を織り込んだ帰無（10-07）は次の窓の予測分布そのもので、警報は「実値が予測の外に出た」を意味する。予見のうち外れを判定する側は既にある |

draft の方向は lighthouse の実測で支持された。ただし「予測を出せば判断が裏付けられる」は成り立たず、予測と実値のずれを
誤警報率が分かる形で測る基準が先に要る、という順序の訂正が入った。draft の「検証タイミング」の節はこの順序で書き直す余地がある。

## 3. Brain の振る舞いについての実測（lighthouse）

- ClaudeBrain（Sonnet 5）は、どのレンズで見直すべきかは正しく提案したが、いつ、何に対して提案するかはノイズに近かった
  （何も起きていない agent にも同程度の頻度で提案した）。primary へは上げておらず、shadow 併走のまま記録だけを取っている。
- 何も起きていない区間（QUIET）で、Sonnet 5 は 59.1% の審議で何かを提案した。その大半（54.5%）は戻せる
  観測変更（`replayRequest`）で、断定的な提案は 4.5%（curator の設計値 4.55% と同水準）だった（2026-08-18）。
- 散文の指示による規律は、指示したチャネルではなく多用されていたチャネルの提案を減らした
  （Sonnet 5 では断定は 4.5% から 8.0% で動かず、観測変更が 54.5% から 4.0% に落ちた）。
- このため lighthouse は、確認を集める場所を AI への指示ではなく、コードの側で決定の型ごとに決めるとした。

wrap の「What Brain AI may and may not do」と PostBox による分離は、この実測と整合する。加えて、決定の型ごとに
戻せるかどうかを宣言し、戻せない型に確認を集める、という規則を仕様に足す価値がある。

## 4. 看板の見直し（提案）

DCP には二つの半分があり、README と dcp-docs の看板は価値が低い方に付いている。

価値が低いと見る方。トークン削減の形式としての DCP（位置配列、Agent Profile による密度の調整）。

- トークンの単価は下がり、コンテキストは伸びている。モデルは JSON を問題なく読む。
- dcp-docs の研究結果も「形式はボトルネックではない」で、削減しても損はないと同時に、差別化にもならないことを示している。
  根拠は 0.5B から 3.8B の小型モデル（format-comparison の表は 3 モデル × 2 課題 × 各 3 回）で小さい。
- 構造化データの形式は MCP（2026-07-28 版で `structuredContent` が任意の JSON Schema を許す）や tool calling の側で標準化が進む。
  張り合うより、その上に乗る方がよい。
- 位置配列は、スキーマの変化に弱く、人が追って確かめることができない。
- dcp-docs の index にある Native Operations の紹介文（"for brain AIs that operate on positional arrays without decoding"）は、
  「AI must never enter the data pipeline」（`PIPELINE_ARCHITECTURE.md`）とぶつかって見える。本体の `docs/dcp/implementation.md` の
  Native Operations は「仕様ではなく観察」と断った設計ノートで、位置配列を decode せずに処理できるのは処理器であり、Brain AI には
  触れていない。ぶつかっているのは index の言い回しだけである。

価値が高い方。推論を経路に入れないための制御の規律としての DCP。

- データの経路（同期、決定的）と制御の経路（非同期、確率的）の分離。Brain は PostBox に提案を書くだけで、適用は PipelineControl が行う。
- quarantine、差し替えられる解釈の層（$V、$R、$P）、境界でのスキーマの握手（`$S!`、`$S+`、`$SV`）。
- 決定の追跡（`$O` の係数、`$ST-O` の値、Brain の理由、MappingLayer の差分）と、PostBox Recorder の記録と再生。
- 業界がエージェントの運用で作ろうとしているもの（policy-as-code、承認の段、監査の記録）と同じ方向で、DCP は先行している。

提案。看板を「データのコスト」から「推論を経路に入れない規律と、宣言と、較正された観測」へ移す。
README の「Two things in one package」は順序を入れ替え、パイプライン制御を先に置く。名前を変えるかは別に判断する。

## 5. 次の共通課題（提案）

基盤と呼ぶには、次の二つが欠けている。どちらも VCP と lighthouse の欠陥から出たものである。

1. 宣言の形式の共通化。スキーマ、値の集合（$V）、公開範囲（$P）に加えて、決定の型ごとの「戻せるか」を一つの宣言で持つ。
   VCP も書き込み先と値の集合を宣言で持つので、形式を寄せられる余地がある（VCP は別のプロトコルのまま参照し合う）。
2. 出所と状態の軸。誰が書いたか（人、AI、bot、規則）と、どの状態か（実値、仮想、提案、確定）を、body ではなく
   専用の軸で持ち、読み手はすべてその軸を見る。欠陥の実例は二つある。lighthouse では、印を付けたが読み手が見ていなかった
   （`aggFuncUnscored`、2026-08-25）。VCP では、履歴が書き込み元の軸を持たずに実装され、AI が書いて確定しなかった値が、
   次の通常モードの起動時の復元で画面に載り、PdfAdapter では原本まで届く経路ができていた（2026-09 に C100、C115 で修正済み）。`$F` と仮想ストリームを入れると、この軸が無いまま仮想値が実値として読まれる経路が増える。

相互に足せるもの。wrap の PostBox Recorder は inbound と outbound を JSONL で記録し、`replay()` で Brain を差し替えて再生できる。
lighthouse は ClaudeBrain の生の出力を残しておらず、審議の再生を課題に挙げている。wrap の記録と再生の作法を lighthouse へ
持ち込める。

## 6. 外の動向（2026年）

- MCP 仕様 2026-07-28 版は状態を持たない方式になった。プロトコルのセッションは廃止され（SEP-2567）、呼び出しをまたぐ状態は
  サーバが発行するハンドルを引数で渡す形になった。変化の通知は `subscriptions/listen` に一本化され（SEP-2575）、拡張の草案
  MCP Events（Triggers & Events Working Group、`experimental-ext-triggers-events`）ではサーバからエージェントへ外の出来事を
  Webhook で届ける。草案のまま ChatGPT が対応を始めた（2026-09-29 の DevDay で発表）。エージェントが依頼を待たずに出来事を
  受けて動く経路が増える。
- arXiv:2610.03140 "Tracking State Footprints: How Agents Can Transact"（Mraz ほか、cs.DB、2026年10月、査読前）。
  コーディングエージェントでは git が取引の下地になるが、多くの領域（供給網、スケジューリング、障害対応）にはその下地が無く、
  効果は即座に見え、しばしば戻せないと指摘する。人の確認の段は今の安全策だが、時間の制約のある仕事は自律の実行を求める、とも書く。

両方を合わせると、人がいないまま始まる書き込みと決定が増える。決定的なデータの経路、提案に限られた推論、較正された証拠、
境界の記録の組は、その下地の一つの形になりうる。

## 7. 人と AI が混ざる情報の生態系

人がシステムの中で果たしている役割は三つに分けられる。意図の出所（入口）、不可逆の境界での承認（決定）、宣言を書くこと
（何が許され、何が戻せるか）。

ユーザの見方は「システムに人間はいらない」である。これは議論の一つの視点として置く。入口と承認については多くが成り立つ。
入口は AI や他のシステムが大半を占めるようになり、承認は較正された証拠があれば多くの境界で機械に移せる。
DCP の「Math first. AI for exceptions.」は、「機械が先、人は例外」へそのまま延長できる。

宣言を書く役割は残ると考えられる。宣言を AI が書くようになっても、その宣言を誰が許したかという問いが一段上へ移るだけで、
どこかの人か制度で止まる。説明責任も同じ場所に残る。正確な形は「人は実行時から抜け、宣言と例外に残る」である。
このとき lighthouse の役割は、承認を機械へ移せるかどうかを、誤警報率という数で決めることになる。

## 8. 運用と還元の記録

- 還元の単位。lighthouse の節目ごとに、何が確かめられ、draft のどこを直すべきかを、この節へ数行で足す。
- dcp-docs の看板（index の Positional Arrays と fewer tokens）は、§4 の方針が決まってから書き換える。
- 語の衝突。VCP にも Shadow という語がある（書き込み前の、確定していない値を持つ作業領域）。DCP の shadow（body に重ねる解釈の層）
  とは別の概念である。両者を並べて語るときは定義を分けて書く。
